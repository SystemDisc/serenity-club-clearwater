# Admin UX audit — Serenity Club of Clearwater

Audit date: September 15, 2026, EDT. This report records the pre-implementation findings. The core implementation is now deployed and authenticated production workflow verification is pending; tested changes and outstanding work are tracked in the companion [improvement plan](../plans/2026-09-15-admin-ux-improvements.md). Authenticated production upload/publishing acceptance and volunteer validation remain outstanding. The [meeting migration review](2026-09-15-meeting-migration-review.md) preserves all 11 legacy schedules without treating unconfirmed format assignments as facts.

## Assessment

Keep Payload and build a simpler editing experience around the club's work. The current admin exposes the underlying content collections and template features more prominently than the tasks volunteers need to complete. Changing labels will help, but monthly events and dues reminders, reliable meeting schedules, bulk gallery publishing, and albums need changes to their workflows and data models.

The four most important conclusions are:

1. **Meeting editing can produce incorrect public information.** A live meeting labeled “Monday through Saturday” is omitted from Tuesday's “Today” list. The parser also cannot distinguish the second Wednesday from other Wednesdays. A single “Open discussion and book study” label applies to every occurrence, although the user confirms formats differ by day. The correct day assignments still need group confirmation; existing prose is not proof.
2. **Bulk uploading is not bulk gallery publishing.** Payload can upload multiple files, but the club's gallery requires a separate record for each photo. There is no album model or album workflow. The main gallery list has no thumbnails; 17 of its 19 entries have identical titles.
3. **Editors cannot readily see or verify their work.** The monthly flyer appears as a 40-pixel thumbnail in the event form. Important collections lack public preview, autosave, and visible publication status in their lists. The mobile image picker is a horizontally scrolling table of long filenames and tiny pictures.
4. **Recurring public information is hidden behind misleading fields or fixed in code.** The About-page dues reminder is actually the Club Settings “Logo Image,” currently an August graphic. Hours, group details, and sponsorship copy have separate sources that ordinary editing does not update. Each maintained section needs an obvious editing destination and a preview of its actual use.

Longer term, an optional DOCX assistant can propose structured event records while keeping the original document and rendered flyer. This is a useful extension after the ordinary monthly workflow works; it must not become a prerequisite for publishing a flyer.

Design for the editors' stated lack of technical experience, occasional use, and need for confidence. Age alone does not establish a disability or preferred device. Larger controls, readable text, obvious choices, visible results, and recoverable mistakes benefit this particular audience without requiring a separate “senior mode.”

## Existing strengths to preserve

- The platform already supplies authentication, access control, draft/published states, version history, relationship pickers, bulk file upload, and extensible admin components. A CMS migration is not justified by these findings.
- Club collections have drafts and 25 saved versions; Pages and Posts have autosave, 50 versions, and preview configuration. These foundations can support understandable editing without building a second CMS.
- Thumbnails in the examined production forms and picker now load. Public gallery images also loaded at phone width. The earlier storage corruption and repair are covered in the [platform reliability audit](2026-09-15-platform-media-isr.md); small, difficult-to-use thumbnails are a separate UX problem.
- The image-editing dialog has a larger preview, crop controls with keyboard descriptions, and numeric alternatives. Escape closed it and returned focus to “Edit Image.” Preserve this behavior while simplifying its entry point and labels.
- Published-content cache invalidation, access checks, stable gallery ordering, pagination, and storage repair safeguards already exist. New admin workflows must use those mechanisms.
- The basic gallery creation form fits at 390 pixels without page-wide overflow. Its language and image picker are the larger problems.

Payload supports custom dashboard, collection, and document views; selective customization is practical. The recommended task screens are an application design built on these extension points, not an out-of-the-box Payload “club management” feature. [Payload custom views](https://payloadcms.com/docs/custom-components/custom-views).

## Findings

Priority: **P1** = address in the first implementation sequence because it affects correctness or a core task; **P2** = substantial usability/recovery improvement; **P3** = prepare for a later feature launch. Priorities do not imply that every item belongs in one release.

### Finding A01 — The dashboard is a collection directory, not a useful starting point (P1)

**Observed/source:** Nineteen destinations appear in the sidebar and dashboard. The nine general/template collections precede the ten club destinations. “Browse by Folder” is the first prominent action, despite zero folders. The dashboard's only custom guidance is a sentence about managing “collections” and a public-site link.

**Effect:** An occasional editor has to remember that this month's flyer is an Event, public photos are Gallery Items, uploaded photos are Media, and homepage images are in Club Settings. Technical destinations such as API, Search Results, Redirects, and Categories compete with ordinary tasks.

**Recommendation:** A task dashboard with “Update this month's flyer,” “Update dues reminder,” “Change a meeting,” “Add photos,” and “Create an album”; current-month status, recent drafts, and direct public-page links. Show a small routine navigation with less frequent content and manager settings secondary. Use names matching the website and work, not database terms. Recognition through visible choices is preferable to requiring editors to remember paths. [NN/g recognition and recall](https://www.nngroup.com/articles/recognition-and-recall/).

### Finding A02 — Monthly events have no monthly workflow (P1)

**Observed:** The monthly entry is “August 2026 Events,” with Date Label = “August 2026” and Time Label = “See flyer.” The public Events page still presents that entry as current during September. This observation does not prove a September flyer exists or establish an editor's intention.

**Source:** Events stores free-text date/time labels, category, summary, image, and numeric order. It has no month/year identity, structured occurrence date, expiration, archive, or dedicated replacement flow. Homepage selection is the first three ordered events.

**Effect:** Updating the month requires finding the right record and coordinating title, date label, image, and summary. Old content never becomes visibly overdue in admin. Individual events and recurring meeting announcements share an undifferentiated list.

**Recommendation:** Separate the editing tasks “Monthly flyer” and “Individual event,” with current/next month, full readable flyer preview, a clear public destination, and a deliberate archive policy. Preserve the ability to publish a flyer without transcribing a full calendar, but provide an accessible text account of essential dates/details.

### Finding A03 — Free-text meeting schedules are misinterpreted publicly (P1, correctness)

**Observed:** Feelings is stored as “Monday through Saturday.” On the public page's Tuesday “Today” list it was absent, although it appeared in the full schedule.

**Source/reproduction:** The actual meetingRunsToday function recognizes “daily,” a substring matching today's weekday, and the special phrase “monday through friday.” Running its body against weekday names produced:

| Stored wording | Days the current function matches |
| --- | --- |
| Daily | All seven days |
| Monday through Friday | Monday–Friday |
| Monday through Saturday | **Monday and Saturday only** |
| Second Wednesday of each month | **Every Wednesday**; there is no date/ordinal input |

The Board of Trustees record uses the last pattern. The time sorter also accepts a narrow text format and does not validate hour/minute ranges. This is not an editor training problem.

**Recommendation:** Structured weekdays, local time, weekly/monthly recurrence, and a generated human-readable summary. Use America/New_York and test month boundaries, daylight-saving transitions, and exceptions. Correct today's interpretation before building more UI on it. Because the page uses ISR, also account for the date changing without a CMS save; the existing five-minute interval is request-driven, not a midnight scheduler.

### Finding A04 — Related meeting information can disagree after a successful edit (P1)

**Source:** The schedule's “AA group formats,” “NA group formats,” business-meeting details, and amenities are hardcoded in the route. Board and speaker meetings also exist separately in Events. An editor changing Meetings cannot update all of those references from one place.

The live TGIF description and fixed group notes both claim particular Tuesday/Thursday studies. These are duplicated legacy claims, not independently verified evidence of the current schedule. The user's correction requires checking them with the group before migration, rather than copying those claims into structured fields as confirmed facts. A25 addresses the missing per-day format model.

The Meetings form also exposes External URL, which is mapped into data but not rendered by MeetingList. Numeric Order does not determine the time-sorted public schedule.

**Recommendation:** Make one meeting record authoritative for recurring details. Put group notes with the relevant group/meeting and derive public displays from it. Allow an event to reference a meeting rather than copy its schedule. Remove controls with no visible effect or clearly define their purpose.

### Finding A05 — Bulk uploads stop before the task is complete (P1)

**Observed:** Media has a Bulk Upload action and its file input supports multiple files, although the visible chooser says “Select a file.” Gallery creation offers one Image, “Create New,” or “Choose from existing.” It has no multi-photo publishing action.

**Source:** Each Gallery Item relates to one Media record. There is no service that turns an uploaded batch into draft gallery entries.

**Effect:** Uploading 30 photos still leaves 30 separate gallery records to create and publish. “Upload succeeded” can reasonably be mistaken for “photos are on the website.”

**Recommendation:** One **Add photos** flow: select files or existing library photos → choose main gallery or album → review thumbnails and shared details → publish the selected ready photos. Give separate counts for uploading, processing, ready, failed, and published. Keep successful uploads when one fails. Native Payload bulk upload is useful infrastructure, not completion of this workflow. [Payload uploads](https://payloadcms.com/docs/upload/overview).

### Finding A06 — Albums are missing, and folders would not solve that (P1)

**Source/inventory:** No album collection, gallery membership relationship, cover, album publication state, or album route exists. Media folders are enabled but unused.

**Recommendation:** Introduce an explicit album with title, optional event/date/description, cover, photo membership/order, and draft/published state. Ungrouped photos must remain first-class. An upload batch should not automatically force an album. Specify visibility rules before implementation, including what happens when an album is unpublished. Payload folders organize records internally; public album behavior is application work. [Payload folders](https://payloadcms.com/docs/folders/overview).

### Finding A07 — Photos are difficult to recognize and select (P1)

**Observed/inventory:** The Gallery Items list shows title, category, order, and update date, with no image. Seventeen bowling entries have identical titles. The existing-media picker searches by filename and shows ten rows per page; filenames contain long storage suffixes. Alt and Caption columns are empty for every current media record.

The event form's selected flyer measured **40 × 40 CSS pixels**. At 390-pixel width, picker thumbnails measured about **37 × 37**, and its table was approximately **723 pixels** wide inside a **374-pixel** scroll region. The screenshot showed filenames running into neighboring cell content.

**Recommendation:** A visual grid, large selectable thumbnails, separate “View larger” and “Use photo” actions, upload-date/album filters, useful display names, and a clear selected count. Do not change storage filenames to improve labels; keep the repaired Blob identifiers separate from editor-facing names. A larger preview exists in the Media editor, but it is too remote from the primary selection task.

### Finding A08 — Text, controls, and narrow layouts need targeted accessibility work (P1)

**Observed:** Sampled form labels are 13px. Desktop Save/Publish buttons were 32px high; mobile equivalents were about 30px. Event image edit/remove buttons were 24 × 24 and appeared unnamed in the accessibility snapshot; the document action menu was also unnamed. Not every button is affected.

At 320px, the event page measured 327px wide and some metadata/filename content extended beyond the viewport. At 390px, the basic gallery form itself fit, but its picker required horizontal scrolling. The inspected session used dark mode; that is not proof dark mode is forced or inaccessible.

**Recommendation:** Start with 16–18px ordinary editing text and approximately 44px primary targets as product design choices, visible action labels, larger previews, accessible names, focus indicators, and responsive cards. WCAG 2.2 AA's target-size criterion is 24px with exceptions; 44px is a more comfortable design target, not an AA requirement. Do not infer a contrast failure from the screenshot alone. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Retest 200% text enlargement and 320px reflow, including errors and dialogs; responsive viewport checks here are not a substitute for actual browser zoom and assistive-technology testing. [Resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

### Finding A09 — Preview and work preservation are inconsistent (P1)

**Source/observed:** The frequently used club collections have drafts/versions but no autosave or admin preview configuration. Events and Meetings forms show Save Draft and Publish changes without a nearby rendering of their public card/page. Pages and Posts, which currently have no content, get autosave and preview infrastructure.

**Recommendation:** Preview the actual affected content beside or immediately below the form, with phone/computer views where meaningful. Add protected draft preview through the existing authentication path, and clearly distinguish “Saved privately” from “Published on website.” Autosave should preserve meaningful draft work without filling lists with anonymous empty records. Do not silently overwrite a public image while claiming the parent content is only a draft.

Live Preview supports collection/global configuration and responsive preview sizes, but the application must supply the correct frontend rendering and draft data. Merely adding a preview button to a cached public URL would not solve the problem. [Payload Live Preview](https://payloadcms.com/docs/live-preview/overview), [drafts](https://payloadcms.com/docs/versions/drafts).

### Finding A10 — Publication status and success are not obvious enough (P1)

**Observed/source:** Default Events, Meetings, and Gallery list columns omit publication status. The forms have status labels, but no persistent “View this on the website” action. Globals and Media use Save, which affects public/shared content, while club collections offer draft/publish.

**Recommendation:** Consistent textual states: Draft; Published; Published with unpublished changes; Processing/Needs attention where applicable. Explain the scope of Save for shared files/settings. After publication provide the exact public destination and a durable result message. Preserve draft-versus-published data separation.

The preceding reliability work addresses cache invalidation. A CMS success toast alone does not prove public rendering, and an already open public page does not receive a push update. Future task screens should preserve the existing transaction-completion invalidation and offer clear recovery if a public refresh fails. See [publishing behavior](../operations/publishing.md).

### Finding A11 — Mistakes are harder to undo than they should be (P1)

**Source/observed:** Content deletion is available to authenticated editors; no project collections enable Payload Trash. Media has no project version history or “used in” reference panel. Removing a Gallery Item, removing a file relationship, replacing shared Media, and deleting a Media file are materially different operations but are not explained together.

**Recommendation:** Make “Remove from gallery/album” the routine action. Add recoverable trash for content and guarded permanent deletion for files, with usage information and explicit affected items. Test storage retention/restoration and revalidation with this Blob adapter before assuming enabling Trash protects every object. Version history helps recover edits; it is not the same as restoring deleted records/files. [Payload Trash](https://payloadcms.com/docs/trash/overview).

### Finding A12 — Photo selection permits incomplete or unsuitable entries (P1)

**Source:** Gallery Image is optional. The alternative external URL is also optional. The gallery can therefore contain a published title with no photo. Upload fields do not filter Media to suitable image types, and the library accepts general files. URLs are plain text fields.

**Recommendation:** Drafts may be incomplete; publishing a gallery photo must require a usable image. Filter choices by supported type, validate URLs and file compatibility server-side, and show a helpful recovery message. Keep external image URLs under advanced options only where needed. Test actual phone HEIC/HEIF support before advertising it; acceptance by the picker alone does not prove conversion/rendering works.

### Finding A13 — Accessible descriptions and visible captions are confusing (P1)

**Inventory/source:** All 44 Media records have no alt text and no caption. Gallery can override alt text and falls back to media alt/title, so this is not proof every public image lacks an alt attribute. Seventeen repeated gallery titles are nevertheless weak descriptions of distinct photos.

Media Caption is used in template rich-content blocks, but the public gallery uses Gallery Item Description. An editor can fill “Caption” and see no gallery change. The monthly flyer alt says it is a monthly flyer; it does not convey the dates and details printed within it.

**Recommendation:** Distinguish “Caption shown below this photo” from “Description for people who cannot see the photo,” with short examples and a visible preview. Supply essential flyer information as text, not only a picture or a very long alt attribute. Provide a contextual decorative-image choice where appropriate; gallery documentation should not imply that every image can safely rely on its title.

An accessible CMS must both work for its authors and help them publish accessible content. This is the relevant ATAG principle, beyond checking the public website alone. [W3C ATAG overview](https://www.w3.org/WAI/standards-guidelines/atag/).

### Finding A14 — Word conversion has a hidden, important limitation (P1)

**Source:** The DOCX pipeline validates documents with 1–25 pages but calls rasterizeFirstPage and replaces the Media record's file with the resulting image. There is no editor-facing page-selection/multi-page outcome in these forms.

**Effect:** A multi-page document can appear successfully uploaded while only page one is presented. Editors also lack a clear distinction between the editable source document and its website image.

**Recommendation:** A dedicated flyer flow that explicitly supports a single-page image/document, or a deliberate multi-page workflow. Reject unsupported page counts with a useful explanation instead of silently dropping pages. Preserve the original DOCX and rendered preview as separate, linked assets: the requested future extraction/reuse makes source retention a requirement. Keep source versions when a flyer is replaced; a source download for editors need not be a public download. Show conversion progress/failure and require preview review before publication. Full production DOCX upload remains an acceptance test; prior work verified rendering locally. The current transformed Media file alone cannot be assumed to contain a recoverable original.

### Finding A15 — “Internal link” excludes the pages people actually need (P2)

**Source/observed:** Internal navigation links can reference Pages or Posts only. Both are empty. Existing main-site routes such as Meetings use “Custom URL” with a manually entered path. The top-menu editor visibly shows /meeting-schedule in that field.

**Recommendation:** “Page on this website” should include all built-in routes plus custom pages/news. “Another website” should take a URL. Rename Label to “Text shown in the menu,” offer a preview, and make reordering usable without dragging alone. Footer guidance currently says empty navigation falls back to header links, while current getSiteNavigation preserves an empty footer: correct the instruction. [W3C dragging alternatives](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

### Finding A16 — The future news editor is a useful foundation with the wrong defaults (P3)

**Observed/source:** Posts exposes Content, Meta, and SEO tabs; Hero Image, Authors, Published At, and Slug; and Code, Media Block, and Banner in its block menu. The project explicitly narrows root Lexical features, so ordinary bullet/numbered lists and blockquotes are absent despite Payload supporting them. H1–H4 are enabled inside content.

Opening Create automatically saved a blank draft displayed as “1.” The cleanup described above verified that this was not a published post.

**Recommendation:** A curated writing screen: title, optional cover, rich body, visible formatting toolbar, preview, saved state, and Publish. Add headings below the page title, lists, links, quote, image/caption, and accessible image guidance. Hide technical blocks and advanced SEO. Test Word/Google Docs paste and keyboard editing. Keep URL generation automatic and provide an understandable discarded-draft experience. These feature exports are present in installed Payload 3.89.0. [Payload rich-text features](https://payloadcms.com/docs/rich-text/official-features).

### Finding A17 — News needs a public launch, not just an admin rename (P3)

**Source:** Post routes have noindex/nofollow metadata; robots excludes /posts; the sitemap queries Pages and Products, not Posts; public Search returns 404. Post-list query errors are caught and converted into empty results, unlike the corrected main club collection loaders.

**Recommendation:** Before launch, choose a public name/route, align canonical URLs, navigation, sitemap/indexing, archive pagination and search expectations, and test draft isolation and new-post visibility. Remove error-to-empty behavior for the public news listing so outages do not masquerade as “no news.” Scheduled publication is currently intentionally disabled until a supported runner is configured; Published At must not be presented as a functioning schedule control.

### Finding A18 — “Pages” does not edit the existing website pages (P2)

**Source/inventory:** Pages is empty and implements a generic Hero/Content/SEO block builder. The homepage, About, Groups, Reach Out, Ways to Give, and other core routes are purpose-built React pages. Much of their explanatory text, membership/service descriptions, and map configuration is in source.

**Recommendation:** Expose the specific recurring copy editors actually maintain, with “Where this appears” context and preview. Keep stable layout in code. Do not hand volunteers a general page builder merely to let them change a paragraph. Label additional pages clearly and move the builder out of routine navigation.

### Finding A19 — Website details mix unrelated tasks and jargon (P2)

**Observed/source:** Club Settings is one flat form with 18 fields spanning legal identity, public description, contact, hours, donations, social links, and three image/upload-plus-URL pairs. Labels include Hero Image, Hero External Image URL, and Donation Url. There is no draft/version configuration for these globals.

**Recommendation:** Contact & hours; Homepage wording & pictures; About & membership dues; Donation & social links. The field called Logo Image currently controls the dues graphic, while the header renders a separate SerenityMark component: renaming it as a branding control would perpetuate the mistake. Explain each image's location, show its current use, and hide external URL alternatives until requested. Add meaningful change review/recovery for high-impact settings. Keep technical controls distinct from ordinary copy editing.

### Finding A20 — Shop, rules, and team editing need simpler controls too (P2)

**Observed/source:** Shop requires a manually maintained unique Slug and free-text Price, exposes “Square or Stripe Checkout URL,” “Badge,” and “Fulfillment Note,” and lacks public preview. Price text is a display value; the external checkout's amount is not synchronized by this code. Policies uses a plain textarea. Team Members requires a Bio even for a minimal board listing.

**Recommendation:** Automatic stable shop URLs, “Price shown on website” with explicit payment-provider scope, “How to buy or collect this,” image/card preview, and manager review of checkout destination changes. Give club rules simple lists/paragraph formatting with migration-safe rendering. Use “Board & team,” optional short bio, and visible display order. Do not imply this CMS manages orders, payments, or the membership roster.

### Finding A21 — Permission levels are available but not reflected in everyday responsibilities (P2)

**Inventory/source:** All three current accounts are administrators. An Editor role exists and restricts account administration, but ordinary content, files, and navigation remain broadly editable by authenticated users.

**Recommendation:** Agree on responsibilities before changing accounts. Routine editors should independently manage events, meetings, photos, dues reminders, and future news; managers handle access, high-impact settings, and permanent deletion. Hiding a menu is not access control: enforce permissions in APIs, server actions, and file operations. Avoid an approval bureaucracy unless the club actually wants one.

### Finding A22 — Help and error recovery are not tailored to club tasks (P2)

**Observed/source:** The dashboard/login guidance is generic. Forms contain little task-specific instruction. Empty lists say “No Results,” even when a feature has never been used. API tabs and technical filenames are visible throughout.

The login provides email/password fields and Forgot password; the recovery screen explains the email process but labels its action only “Submit.” The password field has autocomplete set to off rather than current-password. That markup warrants improvement and password-manager testing; it does not establish that password managers or paste are blocked in practice.

**Recommendation:** Brief inline examples, useful empty states, “View website,” “Get help,” and a short illustrated guide for each core task. Show specific errors beside the field and a linked summary, preserving entered work. For uploads, distinguish wrong format, oversize file, conversion failure, expired login, and temporary connection failure. Treat uncertainty after a save as recoverable state, not a reason to click Publish repeatedly. [GOV.UK error summary](https://design-system.service.gov.uk/components/error-summary/), [file upload guidance](https://design-system.service.gov.uk/components/file-upload/).

### Finding A23 — Public photo browsing constrains the eventual album experience (P3)

**Observed/source:** The mobile gallery currently renders 19 vertically stacked photo cards. Clicking a photo opens its original storage image in another tab. Pagination supports 24 items per page, but there is no album navigation, in-place next/previous photo viewer, swipe alternative, or return-to-position experience.

**Recommendation:** Design album/photo relationships now so the admin work does not require another migration later. Defer the full public gallery redesign to its requested phase: album covers, efficient thumbnail browsing, accessible viewer with explicit controls, keyboard support, position restoration, captions, and efficient image loading. Keep a usable ordinary-link fallback.

### Finding A24 — The monthly dues reminder is disguised as a logo (P1)

**Observed/source:** About displays a graphic reading “It's time to pay your August membership dues.” Its accessible image name is “Serenity Club of Clearwater logo.” The page obtains it from Club Settings → Logo Image / Logo External Image URL. The header uses a separate SerenityMark component, so this is not the site's actual header-logo control. There is no month, reminder text, effective date, or dedicated dues editor.

**Effect:** An editor looking for a monthly reminder must know an unrelated field name, open a small image selection control, and replace a graphic containing text. Updating the month means preparing artwork. The image's logo description does not communicate the reminder to someone who cannot see it. September's audit found August artwork; whether it was intentionally retained is unknown.

**Recommendation:** A clearly named **Membership dues reminder — About page**, linked from Home's monthly tasks. Show the current public reminder at readable size, month/year, wording, optional artwork, optional membership-information link, and visibility. Prefer a branded template with real text so the month can change without new artwork. Offer an automatic current-month mode in Clearwater time and a clearly visible manual override, subject to club preference. Month-specific artwork must agree with the selected month; do not change text to September while leaving an August image underneath. Preserve the current asset during migration and separate dues notices from actual branding.

Real text supports resizing and customization that text baked into a graphic cannot. Keeping the poster alongside an equivalent text presentation can preserve its visual role. This is an application of W3C's images-of-text guidance, not a claim that all graphics must be removed. [W3C images of text](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html).

### Finding A25 — One format field cannot describe different meeting days (P1, correctness)

**Observed/source:** The live TGIF “Today” card says **Open discussion and book study**. Its full card has the same badge plus prose describing different days. Meetings has just one format textarea for the entire recurring record. MeetingList displays that value for every occurrence; its compact Today mode hides the description containing the day-specific claims.

**User clarification:** Discussion and study happen on specific days, but the correct assignments have not been supplied. The generic combined label is wrong for this use. Neither this report nor the migration should invent those assignments or treat the existing Tuesday/Thursday prose as verified.

**Recommendation:** One weekly editor for the group/meeting, with a readable row or phone card for each day: whether it meets, time, format, optional book/topic, room, and confirmation state. “Same on selected days” should reduce repetitive work without forcing seven independent records. Show defaults and day-specific changes explicitly. Support multiple sessions on a day and the monthly patterns already present; provide dated exceptions separately. A date's public card must use the resolved format for that date, not a catch-all label.

Keep **Who may attend** separate from **Meeting format**. A.A.'s own guidance distinguishes open/closed attendance from discussion, speaker, and study formats; “open discussion” alone should not be used to infer an attendance rule. This classification guidance does not establish any Serenity group's actual schedule. [A.A. meeting types and formats](https://www.aa.org/information-about-meetings).

Use “Needs confirmation” in admin for unknown formats, record who checked them and when, and omit unverified public format badges rather than asserting both formats on every day. Keep independently confirmed days/times usable. Resolve weekly rules, monthly rules, and specific-date changes consistently across Today, the full schedule, homepage summaries, and any future printable/calendar view. Test overlapping rules and preview actual upcoming dates before publication.

### Finding A26 — Core operational copy has fragmented ownership (P2; meeting correctness remains P1)

**Source/live checks:** Reach Out repeats fixed opening hours in its introduction and renders editable hours further down. Its map uses fixed place/embed URLs independent of the editable address. Ways to Give includes a fixed $500 annual sponsorship starting amount even though the Sponsors collection is empty. Meeting access instructions and amenities are fixed route text. Instagram URL is stored/mapped but has no public rendering consumer. Page metadata and the social-share image also have source-controlled defaults separate from ordinary settings.

**Effect:** A successful settings save can update only some visible references, or have no visible effect. An empty collection can be mistaken for an unused public feature. A future meeting migration could also inflate the homepage's “meetings” count, which currently counts records rather than weekly occurrences.

**Recommendation:** Create a public-section ownership map, expose frequently maintained copy through small purpose-specific forms, and derive repeated hours/contact/schedule information from shared data. Preview where a change appears. Keep stable layout in code and technical defaults with managers/developers. Define the meaning of counts before changing the meeting model. Do not offer unused controls without explaining or implementing their public destination.

Add a lightweight **Needs attention** area for an old flyer/dues image, unconfirmed meeting information, and unfinished uploads. “Checked and still correct” should be possible without fabricating a content edit. A temporary closure/change notice with an end date is a useful later extension; changing permanent hours should not be the workaround for one unusual day. There is currently no dedicated notice workflow.

### Finding A27 — DOCX-to-events is a valuable future assisted workflow (P3, opportunity)

**Source/request:** The existing converter creates an image; it does not create structured Events. The user wants both outcomes in future. Retaining the source, distinguishing monthly flyers from individual events, and implementing a review step are prerequisites, not capabilities already present.

**Recommendation:** Upload once → retain original and rendered flyer → optionally extract possible events → review each event against its source → create selected drafts → publish the reviewed set. Offer **Publish flyer only** throughout. Extract document text and tables before resorting to OCR/vision; Word documents contain structured paragraphs and tables, though images, text boxes, and visual calendar layouts need additional handling and fixture testing. This is an architectural direction, not a recommendation to move the Node application to .NET. [Microsoft WordprocessingML structure](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-open-and-add-text-to-a-word-processing-document).

Suggestions must identify missing or ambiguous dates, times, years, and locations rather than invent them. Show the relevant source excerpt/page and simple reasons such as “Time not found.” Make correction and dismissal easy; retain normal manual entry if assistance fails. These interaction choices follow established human–AI design guidance. [Microsoft Research human–AI interaction guidelines](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/).

The plan specifies re-import comparison, duplicate protection, preservation of manual edits, bounded background processing, and acceptance tests. New event suggestions must not silently modify recurring meetings, cancel missing events, or publish themselves.

## Accessibility and nonprofit-specific design requirements

These are implementation criteria, not findings that every current control fails.

| Need | Design requirement |
| --- | --- |
| Readability | Larger ordinary text, comfortable line spacing, meaningful headings, user-selectable theme; measure contrast in both themes. Normal text generally needs 4.5:1 and large text 3:1 for WCAG AA. [Contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| Discoverability | Visible verbs and labels; avoid relying on hover, slash commands, tooltips, icon meaning, or remembered paths. Use the club's own terminology. [W3C older-user guidance](https://www.w3.org/WAI/older-users/developing/) |
| Keyboard/touch | Logical focus order, named controls, focus return after dialogs, browse-file alternative to drag/drop, and clickable move-up/down alternatives to drag sorting |
| Feedback | Persistent upload/save/publication states plus appropriate screen-reader announcements; avoid a toast as the sole completion evidence. [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) |
| Login/recovery | Allow password managers and paste, make password reset/help understandable, preserve meaningful drafts across session expiry; test actual email delivery separately. [Accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) |
| Community photos | Make public visibility explicit; use the club's actual photo-permission practice; do not infer or add attendees' recovery status or names to descriptions. Give a straightforward removal contact/process |
| Volunteer continuity | Short task guides, understandable change history, recoverable mistakes, and manageable account handover; do not rely on one technically confident volunteer |

Uploaded media is currently publicly readable and stored in public Blob storage. A draft Gallery Item is not a private photo vault. If the club needs private photo review before public storage, that is a separate storage/access requirement to design explicitly.
